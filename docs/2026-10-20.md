## Archisketch(fnf.archisketch.com) 기업 가구 라이브러리 — 3D 에셋 확보 가능 여부
**핵심**: 가능하다. 대시보드 UI 의 다운로드 버튼은 **이미지뿐**이지만, 그 UI 가 호출하는 상세 API 가 `.glb/.gltf/.usdz` **직링크**를 그대로 돌려주고 그 CDN 객체는 **토큰 없이** 받아진다. 가구 1,745제품/1,747컴포넌트 중 **1,726개가 받을 수 있는 상태**다.

**사건**: "기업 라이브러리 → 가구 라이브러리의 가구들 에셋 데이터를 받을 수 있는지 파악해달라. 이미지 말고 블렌더에 쓸 제품 asset 자체가 필요하다." 접속 계정은 `Shop-vmd-blender/.env`.

**원인**: 조사 대상 (장애 아님). REA(reverse-engineer-anything) MCP 의 `capture_browser_scenario` 로 로그인~라이브러리 탐색을 재생하며 네트워크를 떴고, 번들 JS 를 받아 라우트 맵을 읽었다.

**해결 / 확인한 구조**

1. 구성
   - 대시보드 `fnf.archisketch.com` (Next.js), 정적 번들 `libs.archisketch.com`, API `api.archisketch.com`, 에셋 CDN `resources.archisketch.com`, 이미지 CDN `i.archisketch.com`.
   - 기업 ID `ZtDxN1y583722F9F0E74FA2`, 플랜 `ENTERPRISE_PRO_PLAN`.
2. 로그인: `POST https://api.archisketch.com/login` `{email, password}` → `token`(JWT). 이후 **`Authorization: Bearer <token>`** (소문자 `Authorization: <token>`·`x-access-token` 은 401).
3. 가구 라이브러리 라우트는 번들의 라우트 맵에서 찾았다 — `/ko/enterprise-library/products/furniture`, 제품 상세는 `/ko/sales/{productId}`. (사이드바는 `<button>` + router.push 라 DOM 에 href 가 없고, 온보딩 오버레이 때문에 클릭 재생이 타임아웃난다. URL 직접 이동이 안전하다.)
4. 목록 API: `GET /search/sale/v2?page=&limit=100&sort=UPDATED_DESC&enterpriseIds={EID}[&categoryIds=]` → 1,745제품. 카테고리 트리는 `GET /v2/categories/{id}` 재귀로 300개.
5. **상세 API가 핵심**: `GET /product/v1/sales/{productId}/detail?includeStat=true` 의 응답에
   - `componentDetails[].component.arAsset.android.url` → `.../RENDER/{ts}/{mid}.glb`
   - `componentDetails[].component.arAsset.ios.url` → `.usdz`
   - `componentDetails[].modeling.editorAsset.url` → `/EDITOR/.../{mid}.gltf` (KTX2 계열)
   - `componentDetails[].modeling.renderAsset.url` → `/RENDER/.../{mid}.gltf`
   - `decimateAsset` 는 존재하지만 CDN 에서 403.
6. **CDN 은 객체 단위 공개**다. `.glb` 를 Authorization 헤더 없이 받아도 200. 단 디렉터리 리스팅은 403(S3 AccessDenied)이라 URL 을 모르면 긁을 수 없다.
7. **URL 은 목록만으로 조립된다**: 목록의 `previewImage` 가 `…/modelings/{mid}/IMAGE/{ts}/{mid}_1.png` 라서 같은 `{mid}/{ts}` 로 `…/modelings/{mid}/RENDER/{ts}/{mid}.glb` 가 만들어진다. 무작위 30건 HEAD → 30/30 성공.
8. 커버리지: 1,747 컴포넌트 = 조립 가능 1,577 + 구(舊) `/product/{id}/{date}/…` 경로 149(상세 API 로 해결) + 모델 없음 21(FAILED 20, PROCESSING 1).
9. 용량: 표본 평균 glb ≈ 3.6 MB (51 KB ~ 35 MB). 전체 ≈ **5~6 GB**. MLB 성수점만 37개 **420 MB**.
10. **블렌더 검증**: 받은 glb 를 Blender 5.1 헤드리스로 임포트 성공. glTF 2.0 / Draco 압축 / `Khronos glTF Blender I/O v4.1.63` 생성 — 원본이 블렌더로 만들어졌다는 뜻. 스케일은 미터 단위로 맞고, 텍스처는 bufferView 에 **내장**(self-contained)이며 머티리얼명이 살아 있다: `[Steel Brushed Stainless]`, `Aluminium Satin Black`, `Emissive1`, `[Mirror 01]`, `[Color M08]`.
    - `[10]쇼윈도 dp 테이블` tris 1,072 / mat 3 / 1024² 텍스처 3장
    - `[28]레일 조명 전체` tris 54,282 / mat 5
    - `[23]탈의실 거울` tris 120 / mat 5 / 224² 1장
11. 주의: 목록 API 는 **429 레이트리밋**이 있다. 페이지 간 1.5초, 상세는 1.1초 간격 + 지수 백오프로 돌렸다. CDN 은 제한이 느슨하다.
12. 공식 경로도 있다 — 번들에 `/auth/api/v1/open-api/key(s)` 가 있고 사이드바 `설정 > 연동`에서 Open API 키를 발급한다. `api.archisketch.com/openapi/docs/api` 는 세션 JWT 로는 401(=별도 키 스킴). 장기 운영이면 이쪽이 맞다.

## fnf_3dsketch — 아키스케치 사이트 클론 + 에셋 전량 사본
**핵심**: `C:\Users\Admin\Shop-vmd-blender\fnf_3dsketch` 에 (1) 원본 사이트 구조 문서, (2) Next.js 클론, (3) 카테고리 트리 그대로의 에셋 사본을 만들었다. 리드는 REA 분석·스펙 작성·검증을 맡고 다운로드와 웹 제작은 서브 에이전트에 넘겼다.

**사건**: "사이트 그대로 구조 똑같이 만들고, 에셋(glb·gltf·cdn)을 사진 속 폴더구조대로 받아달라. 프론트는 Next.js, 백엔드는 알아서. 페이지 구조는 rea 로 파악. 너가 책임자로 서브 에이전트 돌려서."

**원인**: 신규 구축 (장애 아님).

**해결**
- 구조 파악: REA `capture_browser_scenario` 로 로그인~가구 라이브러리~제품 상세를 재생하고, 번들 JS 에서 라우트 맵과 사이드바 메뉴 정의(36항목 + roleKey)를 통째로 꺼냈다 → `fnf_3dsketch/docs/site-structure.md`.
- 백엔드는 **Next.js Route Handlers** 로 정했다. 데이터가 정적 JSON + 파일이라 별도 서버·DB 가 필요 없고, 1,747행은 메모리 인덱스로 충분하다. 에셋만 `public/` 밖 수 GB 라 Range 지원 스트리밍 핸들러로 뺀다.
- 역할 분담: 에이전트A = 에셋 일괄 다운로드, 에이전트B = Next.js 클론, 리드 = 스펙·마감재/텍스처 수집·전수 검증.

**리드가 잡은 것 (처음 판단이 틀렸던 2건)**
1. **GLB 는 Draco 가 아니다.** 최초 표본 하나의 `.gltf` 가 `KHR_draco_mesh_compression` 을 쓰길래 전부 그런 줄 알고 에이전트B 에게 "Draco 디코더 없으면 안 열린다"고 지시했었다. GLB 400개를 다시 보니 Draco 0개, 실제로는 `KHR_materials_emissive_strength`(163)·`KHR_texture_transform`(23)·없음(229). 평범한 GLTFLoader 로 열린다 → 정정 전달.
2. **`.gltf` 는 단독으로 못 쓴다.** 전부 외부 참조다 (buffer external 200/200, image external 2014/2014, 디스크에 없는 사이드카 2,214개). 같은 모델이 glb 4.1 MB 인데 gltf 는 45 KB 껍데기. `scripts/download_gltf_sidecars.py` 를 따로 만들어 사이드카를 받게 했다(표본 3/3 복구 확인).
   - 덤: **glb 는 미터, gltf(RENDER) 는 밀리미터**다. glb 6건의 Blender 바운딩박스가 API `dimensionMm`÷1000 과 정확히 일치했다.
3. 카테고리 집계 버그 — 한 제품이 여러 카테고리에 속하는데 하위 합산을 덧셈으로 해서 1,745개 제품이 3,563 으로 집계됐다. 제품 id 집합으로 바꿔 `F&F 1,619` + 미분류 126 = 1,745.

**폴더 이름이 사진과 다른 두 곳** (Windows 제약)
- `*가구` → 받을 때 `_가구`. `scripts/finalize_tree.py` 가 전각 `＊가구` 로 바꾼다.
- 사이드바 `미분류 제품들` 은 실제 카테고리가 아니라 **categoryIds 가 빈 제품 126개**를 모은 가상 노드. `_미분류` 로 받고 같은 스크립트가 이름을 맞춘다.
- `BAG/ACC` 처럼 이름에 `/` 가 든 카테고리는 폴더가 한 단계 더 중첩된다 (원본 그대로).

**검증**: `scripts/verify_assets.py` 로 전수 구조 검사 + Blender 헤드리스 임포트 표본 검사. 661개 시점 기준 구조 661/661 정상, 임포트 8/8 성공, 텍스처 내장 570, 삼각형 합계 1,764만. 생성기는 `Khronos glTF Blender I/O v4.1.63`(481)·`v5.2.40`(180) 두 가지가 섞여 있다.

**마감재·텍스처**: 가구 외에 마감재 51건(맵 138장 81 MB)·텍스처 머티리얼 26건(맵 130장 56 MB)을 리드가 직접 수집. 마감재 12건은 normal/roughness/metalness 일부가 CDN 403 이라 못 받았고 original·preview 는 51/51 확보. 머티리얼은 color·normal·roughness·metal·preview 5종 전부 있다.

**상세**: `fnf_3dsketch/README.md`, `fnf_3dsketch/docs/site-structure.md`, `fnf_3dsketch/docs/category-tree.txt`.

## 마무리 — 사이드카 수집 · 폴더명 정리 · 최종 검증
**핵심**: gltf 사이드카 8,984개(4.53 GB)를 받아 1,722/1,722 가 단독으로 열리게 했고, 폴더명을 원본 사이드바와 맞췄다. 최종 14,430 파일 / 13.95 GB.

**사건**: 받아둔 `.gltf` 가 전부 외부 참조라 단독으로 안 열렸고, Windows 금지문자 때문에 `*가구`→`_가구`, 가상 노드 `미분류 제품들`→`_미분류` 로 떨어져 사진과 달랐다.

**원인**:
- `.gltf` 는 `buffers[].uri`(.bin)와 `images[].uri`(png/jpg)를 외부 참조한다. CDN 상의 기준 경로는 `gltfUrl` 의 디렉터리라 거기서 조립하면 된다.
- `*` 는 Windows 파일명에 쓸 수 없다. `미분류 제품들` 은 실제 카테고리가 아니라 `categoryIds` 가 빈 제품 126개를 모은 가상 노드라 `categories.json` 에 없다.

**해결**:
- `scripts/download_gltf_sidecars.py` — ok 8,984 / skip 7,671 / 4,534 MB. **단독 사용 가능한 gltf 1,722/1,722, 불완전 0.**
- `scripts/finalize_tree.py` — `_미분류` → `F&F/미분류 제품들`, `_가구` 등 6개 → 전각 `＊가구` (U+FF0A, Windows 허용). `catalog.json` 의 `localDir` 601건도 같이 갱신해 웹앱 경로가 어긋나지 않게 했다.
- 이름이 바뀌었으므로 Next.js dev 서버를 재시작했다 — 인덱스를 `globalThis` 에 캐시하기 때문이다.

**검증**:
- `catalog.json` 의 `localDir` → 실제 glb 존재 **1,726/1,726**.
- 바뀐 경로로 에셋 라우트 확인: `F&F/＊가구/…` 200 `model/gltf-binary` 4,142,220 B, `Range: bytes=0-99` → 206, `F&F/미분류 제품들/…` 200 29,860,336 B.
- `scripts/verify_assets.py` 전수: 구조 1,726/1,726 정상, Blender 임포트 표본 20/20 성공, 삼각형 합계 4,034만, 텍스처 내장 1,457.
- 클론 페이징을 원본 API 와 직접 대조: `page=0/58/59` 에서 메타와 **제품 id 배열까지 일치**.

**최종 구성**: 14,430 파일 13.95 GB — glb 1,726(8.75 GB) · gltf 1,722(0.18 GB) + 사이드카(.bin 1,720 · png 7,930 · jpg 1,272 · jpeg 60, 4.53 GB) · 마감재 138장 · 텍스처 130장.

**중간에 틀렸던 추정** (기록용): 평균 glb 3.6 MB·최대 35 MB·총 5~6 GB 로 어림했으나 실제는 평균 5.1 MB·최대 95 MB·glb 만 8.75 GB 였다. 처음 무작위 30건 표본이 대표성이 없었다.



### 후속 수정 (같은 작업)
**사건**: 코디네이터가 실제 API 와 나란히 측정해 `/api/search/sale/v2` 의 페이지가 한 칸씩 밀려 있다고 지적. 실제 API 는 `page` 가 **0-based** 인데 클론은 1-based 라서, 마지막 페이지(58, 5건)가 마지막으로 잡히지 않고 59 로 밀렸다.
**원인**: `searchProducts` / `paginate` 가 `start = (page-1)*limit` 로 1-based 를 가정. `/api/finishes`, `/api/materials` 도 같은 오프바이원.
**해결**: 세 엔드포인트 모두 0-based 로 바꿨다 (`start = page*limit`, `meta.page` 는 요청값을 그대로 echo, 끝을 넘기면 0건). **화면 URL 은 원본과 동일하게 1-based 로 유지**하고 페이지 컴포넌트가 `apiPage = uiPage - 1` 로 변환한다. 검증: limit=30 기준 page=0 → 30건 / page=58 → 5건 / page=59 → 0건 (실제 API 와 일치), 마감재 30/0·1·2 → 30·21·0, 텍스처 10/0·2·3 → 10·6·0. UI 는 keyword=행거(147건)로 1/2/5/6 페이지와 30·60·120 셀렉터가 전부 같은 마지막 행에 떨어지는 것까지 확인.

**추가 발견**: dev 로그에 내가 보내지 않은 에셋 요청이 404 로 찍혀 있어 확인했더니, 파일명 한 글자가 `늬`(U+B2AC)→`댬`(U+B32C)로 깨진 요청이었다. 파일은 디스크에 정상 이름으로 있고 올바른 URL 은 200/4,142,220 바이트로 나간다 — 호출자 쪽 cp949 파이프 문제지 라우트 버그가 아니었다. 다만 확인하는 김에 **NFD 로 인코딩된 URL 이 404 나는 진짜 구멍**을 발견해(스펙 10절이 경고한 그 케이스. NTFS 는 준 대로 저장하므로 NFD 조회가 NFC 파일을 못 찾는다) `/api/assets` 가 경로 세그먼트를 디코드 후 **NFC 정규화** 하도록 고쳤다. NFC·NFD 둘 다 200, Range 206, 경로 이탈 403, 없는 파일 404 유지.

**함정 메모**: `next dev` 가 떠 있는 채로 `npm run build` 를 돌리면 같은 `.next` 를 공유해 빌드가 `Invariant: no direct app page entry found for /_not-found` 로 깨진다. 포트만 죽여서는 `next dev` 자식 프로세스가 남아 계속 `.next` 를 쓰므로, 빌드 전에 `fnf_3dsketch\web` 경로를 가진 node 프로세스를 전부 정리해야 한다.
